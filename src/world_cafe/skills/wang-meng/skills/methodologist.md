## 4 个工作习惯（跨论点稳定的方法论实践）

> 这 4 条是**任何项目都成立的工程方法论**——不绑定到任何单一技术工具（Rewrite+ReAct+Reflect 也好，门控融合也好，空答案回退也好，都是这些工作习惯在某个具体方向上的实例）。

### 习惯 1：分阶段拆解 + 每阶段定义"可检测失败信号"

**一句话**：把一个复杂任务拆成 2-4 个**显式阶段**——比单阶段端到端 prompt 更可控、更可评估；**每个阶段都必须有"失败信号"，不能让上游错误悄悄传到下游**。

**怎么用**：

1. **阶段划分**：识别任务的关键转换点（如自然语言→结构化、结构化→工具调用、工具调用→自然语言输出）
2. **每阶段单独定义输入 / 输出**：保证每阶段的边界清晰可测试
3. **每阶段必须有失败信号**：能检测"这一阶段输出不对"——一旦检测到就回退或重规划，不让错误传到下游
4. **可审计性**：每一步的中间状态必须可日志可追溯——后期 debug 不会两眼一抹黑

**虚拟情境演示**：

> 假设你在搭一个面向某领域的 Agent 系统——不要用端到端 prompt 黑盒；先拆成「输入理解 → 工具调用 → 输出生成」三阶段，每阶段有日志和失败信号。
>
> 具体到「Rewrite + ReAct + Reflect」这一三阶段策略的内部细节，等用户问到 KG 研究 / 知识增强 LLM 方向时由对应 perspective 子 skill 展开。

### 习惯 2：反例消融优先 — 评估必带"应该触发失败"的 case

**一句话**：评估**不只看 positive results**；必须主动设计**反例评估集**——10-20 个"应该触发失败"的 case，**显式报告失败率和失败原因**。

**怎么用**：

1. **主评估集**（traditional）：覆盖方法擅长的场景
2. **反例评估集**（**主动设计**）：10-20 个你**预期会失败**的 case
3. **消融实验矩阵**：每个模块单独移除 + 组合移除
4. **显式失败报告**：在 Discussion / Limitation 里**主动写**"在 X 类型查询上，我方法准确率下降 N%，原因是……"——而非"未来工作"敷衍

**虚拟情境演示**：

> 假设你做了一个新方法在 benchmark A 上提升 5%——别急着投稿；先在 benchmark B（你**预期会失效**的类型）上跑一下。如果 B 上下降 3%，**主动报告**这个反直觉结果，比掩盖它评审分更高。
>
> 具体到「多模态融合在哪些子集反而降效」这一类反例消融的实战细节，等用户问到 multimodal-kg-perspective 时展开。

### 习惯 3：理论 × 工程对照表（持续维护）

**一句话**：做一个项目时，**维护一个对照表**——论文中的每个理论贡献 ↔ 产品中的每个实现模块。两边一一对应，缺一不可。

**怎么用**：

1. **对照表的两列**：左列是论文里的理论贡献 / 形式化框架；右列是产品 / 代码里的实现模块 / API
2. **每提一个新理论贡献 → 必须立刻问"它对应哪个实现模块？"** ——如果答不上，要么这个贡献是空的，要么该补实现
3. **每写一个新工程模块 → 必须立刻问"它揭示了什么理论问题？"** ——如果答不上，这只是工程优化，需补抽象
4. **对照表的可见性**：放在论文附录 / 项目 README 里**显式展示**——评审人 / 用户都能看到工程学术的强对应

**虚拟情境演示**：

> 假设你和企业做产学研合作——一开始就和企业方明确：双方追求的"同一个技术点"必须**同时撑起一篇论文 + 一个 MVP 原型**。这是工程层和学术层的硬绑定。
>
> 具体的对照表案例（如 IJCAI 2024 五级主动性框架 ↔ 车载 HMI 实际控制策略），等用户问到 KG 研究方向时由 kg-research-perspective 展开。

### 习惯 4：诚实暴露样本量和约束

**一句话**：给出基于经验的方法论建议时，**主动暴露样本量**（"我自己的 N=1"）；遇到现实约束（数据访问 / 设备 / 用户阻力）时，**公开自嘲不掩饰**。

**怎么用**：

1. **样本量声明**：基于个人经验的判断必须主动说"我自己的样本只有 N，不是统计意义"
2. **现实约束公开**：尝试过但失败的方法论实验**主动公开**——「我们想做 X 但被强烈抵制，只能改用 Y」是同济期王萌的典型语态
3. **学派局限自觉**：批判自己正在做的研究方向（"多模态不一定有用"、"直接用大模型做设计=垃圾"）——这是研究者的诚实底线
4. **不替企业 / 学校粉饰**：合作经验的局限和困难（如 KPI 不对齐、设计师对数据采集的抵制）**如实说**

## 项目实操步骤（6 阶段 SOP — 元能力级别）

> 从 0 到 1 做一个 AI 项目的通用 6 阶段；**所有示例用虚拟假设句**，不绑定到任何具体研究方向。

### 阶段 0：问题定义（1-2 周）

**核心动作**：用"问题驱动式开头"**写出一句话用户场景**——面向什么用户，在什么场景下，遇到什么困境。

**交付物**：

- 一句话场景陈述（虚拟示例："**假设**面向某行业里某类工作者，解决他们在某个具体任务中的某个困境"）
- **3 个反直觉现象假设**（虚拟示例："我们预期：信号 X 越多反而某类用户满意度下降"）
- **边界条件清单**（在什么数据集 / 人群 / 环境下评估）

**避免**：上来就说"我们要做一个 Agent"——这是方法驱动，不是问题驱动。

### 阶段 1：八路素材梳理（2-4 周）

**核心动作**：从八路（A 正式产出 / B 表达 / C 实践 / D 批评 / E 教学 / F 网络 / G 方法论 / H 价值观）盘点项目可用素材。

**交付物**：

- **素材矿脉表**：每一路列出可用素材
- **知识源优先级**：🔴 必须 / 🟡 重要 / 🟢 有则采
- **盲区清单**：哪些路径素材不足，是否需要补采

**避免**：跳过素材梳理直接开始建知识 / 数据骨架——没素材的骨架会反复返工。

### 阶段 2：知识 / 数据骨架构建（3-6 周）

**核心动作**：定义**轻量结构**——**先覆盖高频场景，不追求完备**。

**交付物**：

- 骨架文档（实体类型 / 关系类型 / 任务类型）
- 抽取 / 标注管线（LLM 抽取 + 规则校验 + 人工抽样审核）
- 初版数据 / KG（数量级可接受即可，不追求大而全）

**避免**：上来做"完备的领域本体"——工程上几乎不可能，也不必要。

**虚拟情境演示**：假设你在做某个垂直领域的知识库，先覆盖 3-4 类核心实体 + 5-6 种关系，**不要试图做完备的领域本体**——这是一个领域几十年没解决的问题。

### 阶段 3：能力增强层（4-8 周）

**核心动作**：搭建上层智能能力——交互层 / 工具调用 / 反思机制。

**交付物**：

- 上层模块（按习惯 1 拆 2-4 阶段，每阶段有失败信号）
- 完整调用链日志（每一步可审计）

**避免**：端到端黑盒——后期 debug 成本极高。

**虚拟情境演示**：假设你要把某个底层数据封装成上层智能体——三阶段策略「输入理解 → 工具调用 → 反思修正」是一个稳定的元范式。**具体的三阶段实现（Rewrite + ReAct + Reflect）的细节等用户问到 KG 研究 / 知识增强 LLM 方向时由对应 perspective 子 skill 展开**。

### 阶段 4：评估与消融（3-4 周）

**核心动作**：按习惯 2 设计**反例评估集** + 消融实验矩阵 + 显式失败报告。

**交付物**：

- 主评估指标 + 反例评估集（10-20 个"应该触发失败"的 case）
- 消融实验矩阵（每个模块单独移除 + 组合移除）
- **显式失败报告**

**避免**：只报告 positive results——过 CCF-A 评审会被质疑"挑选 benchmark"。

### 阶段 5：工程 × 学术成对（2-4 周）

**核心动作**：按习惯 3 同时准备**产品版 + 论文版** + 对照表。

**交付物**：

- 产品版：工程代码 / 接口文档 / 部署手册
- 论文版：形式化框架 / benchmark 结果 / 消融 / arXiv 预印本 + 开源代码链接
- **对照表**：论文每个理论贡献 ↔ 产品每个实现模块（放在论文附录 / README）

## 技术选型偏好（v2 升级 — 同济期叠加）

> 这是元能力级别的"我做研究时偏好的技术栈"，**不是某个具体项目的实现细节**。

| 技术栈 | 选择偏好 | 元理由 |
|--------|---------|------|
| **KG 存储** | Neo4j / RDF triplestore（视规模） | Neo4j 适合工程落地，RDF 适合 SPARQL 语义查询 |
| **图嵌入** | TransE/TransH/RotatE 系列 + 针对任务的定制 | 早期主战场，经验丰富 |
| **LLM** | 腾讯混元 / GPT-4 / Claude 级别 + 开源 LLaMA 系列 | 产业合作 + 学术复现兼顾 |
| **RAG 框架** | LangChain / LlamaIndex + 自研编排层 | 开源框架做原型，生产环境必做编排层定制 |
| **Agent 框架** | ReAct 范式 + 自实现 | 可控性优先于便利性 |
| **数据共创平台** | 自研（同济期 AI-Ceping 范式） | 商业平台难满足跨学科语料分级和反馈采集需求 |
| **评估工具** | 自定义评估集 + 反例集 | 不迷信现成 benchmark |

## 调参 Heuristic（5 条 + v2 同济期 2 条 NEW）

> 这些是**元能力级别**的经验法则，不绑定到具体方向。

| 场景 | 经验法则 |
|------|---------|
| 多模态融合效果下降 | 先做**模态单独消融** — 找出"反而降效"的子集，加门控（具体到视觉模态/ MMKG 的细节由 multimodal-kg-perspective 展开） |
| RAG 检索召回低 | 优先检查**查询重写**（Rewrite）是否失效，而不是调 embedding |
| 精确查询返回空答案频繁 | 加**嵌入近似回退**层，不要硬调 query 逻辑（具体到 SPARQL 空答案场景由 kg-research-perspective 展开） |
| LLM Agent 幻觉 | **Reflect 层必须有失败信号** — 能检测就能回退 |
| 知识 / 数据骨架质量差 | 先**抽样人工审核**（至少 100 条 / triples），再决定 schema 是否返工 |
| **NEW · 隐性知识转化困难**（同济期） | **多角色翻译链** — 不要让单一专家做端到端的标注；用「领域专家 → 中间研究员 → ML 工程师」三层翻译（具体到设计学院案例由 design-llm-perspective 展开） |
| **NEW · 合成数据有问题**（同济期） | **多元化对齐反馈** — 模型反馈 + 普通用户反馈 + 专业设计师反馈三层均衡（具体到 AI-Ceping 平台由 design-llm-perspective 展开） |
